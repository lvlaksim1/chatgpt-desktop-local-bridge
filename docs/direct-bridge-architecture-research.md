# Исследование прямого моста ChatGPT ↔ компьютер

Дата: 2026-10-07

## Цель

Проверить по работающим исходным кодам, как надёжно реализовать прямой цикл:

`текущий ChatGPT → локальный мост → терминал/процесс/файлы → результат → тот же ChatGPT`

без обязательного второго планировщика.

## Изученные реализации

### YosefHayim/ai-browser-bridge

Исходники:
- https://github.com/YosefHayim/ai-browser-bridge/blob/main/src/features/providers/chatgpt/chatgptPage.ts
- https://github.com/YosefHayim/ai-browser-bridge/blob/main/src/features/bridge/orchestrator.ts

Полезные механизмы:
- до отправки фиксируется исходное состояние диалога;
- ввод в поле ChatGPT и нажатие отправки не считаются доказательством успешной отправки;
- после отправки ожидается наблюдаемое изменение диалога;
- при неопределённом состоянии не выполняется слепой повтор, если уже есть признаки начавшейся генерации;
- завершение ответа определяется по устойчивому состоянию, а не одному мгновенному признаку.

### DrA1ex/chatgpt-bridge

Исходники:
- https://github.com/DrA1ex/chatgpt-bridge/blob/main/tools/chrome-bridge-extension/content/requestPromptCommands.js
- https://github.com/DrA1ex/chatgpt-bridge/blob/main/tools/chrome-bridge-extension/background/outboxV5.js
- https://github.com/DrA1ex/chatgpt-bridge/blob/main/tools/chrome-bridge-extension/background/stateV6TransportReducer.js

Полезные механизмы:
- отдельные идентификаторы запроса и команды;
- фиксация исходного множества сообщений перед отправкой;
- успешная отправка подтверждается появлением нового пользовательского сообщения;
- состояния «отклонено до отправки» и «неопределённо после начала отправки» разделены;
- критические исходящие сообщения сначала сохраняются, затем отправляются;
- сохранённое сообщение удаляется только после подтверждения доставки;
- повторная доставка отделена от повторного выполнения действия.

### alexanderradahl/mac-developer-bridge

Исходник:
- https://github.com/alexanderradahl/mac-developer-bridge/blob/main/bridge.mjs

Полезные механизмы:
- ChatGPT остаётся единственным планировщиком;
- локальный мост предоставляет детерминированные инструменты;
- одноразовые команды, фоновые процессы и интерактивный терминал разделены;
- настоящий псевдотерминал имеет отдельные операции открытия, чтения, записи, изменения размера и закрытия;
- вывод хранится в ограниченном кольцевом буфере;
- чтение идёт по абсолютной позиции, поэтому повтор того же чтения безопасен;
- возвращается количество потерянных байтов, если потребитель отстал от размера буфера;
- терминальные секреты и ввод не пишутся целиком в журнал;
- при остановке уничтожается группа процессов.

### Microsoft Terminal — ConPTY GUIConsole sample

Исходники:
- https://github.com/microsoft/terminal/tree/main/samples/ConPTY/GUIConsole
- https://github.com/microsoft/terminal/blob/main/samples/ConPTY/GUIConsole/GUIConsole.ConPTY/PseudoConsole.cs
- https://github.com/microsoft/terminal/blob/main/samples/ConPTY/GUIConsole/GUIConsole.ConPTY/Processes/ProcessFactory.cs
- https://github.com/microsoft/terminal/blob/main/samples/ConPTY/GUIConsole/GUIConsole.ConPTY/Terminal.cs

Полезные механизмы:
- Windows ConPTY создаётся через `CreatePseudoConsole`;
- ввод и вывод идут через отдельные каналы;
- дочерний процесс получает `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`;
- размер терминала управляется отдельной операцией;
- ConPTY даёт реальные терминальные семантики, которых нет у простого перенаправления стандартного ввода/вывода.

### rp10000/chatgpt-native-bridge

Исходник:
- https://github.com/rp10000/chatgpt-native-bridge/blob/main/src/workspace/shell-runner.js

Полезные механизмы:
- одноразовый запуск процесса остаётся отдельным инструментом;
- вывод и время выполнения ограничены;
- stdout и stderr разделены;
- дерево процесса уничтожается при остановке;
- политика разрешений отделена от исполнения.

## Принятая архитектура проекта

### Обычный путь

```text
пользователь
  ↓
текущий диалог ChatGPT
  ↓
LOCAL_BRIDGE_REQUEST_V1
  ↓
WebView2 → C# Local Bridge
  ↓
локальный инструмент
  ↓
LOCAL_BRIDGE_RESULT_V1
  ↓
тот же диалог ChatGPT
```

Текущий ChatGPT является планировщиком. `local.intent` не участвует в обычном пути и сохраняется только как экспериментальный/дополнительный механизм.

### Одноразовые команды

`process.run` остаётся ограниченным неинтерактивным запуском. Он не заменяется терминалом.

### Постоянный терминал

Используется Windows ConPTY:

- `terminal.open`
- `terminal.read`
- `terminal.write`
- `terminal.resize`
- `terminal.status`
- `terminal.close`

Процесс создаётся приостановленным, помещается в Windows Job Object и только затем запускается. Это исключает окно между запуском процесса и установкой ограничения дерева процессов.

Вывод хранится локально в ограниченном кольцевом буфере. ChatGPT читает только нужные новые данные по абсолютному курсору; поток вывода не превращается в поток сетевых сообщений.

### Доставка результата в ChatGPT

Доставка считается доказанной только после появления точного нового пользовательского сообщения с ожидаемым служебным содержимым.

Очистка поля ввода сама по себе не является доказательством.

Состояния разделены:

1. действие отклонено до начала отправки — безопасен повтор;
2. отправка началась, но появление сообщения не доказано — автоматический повтор запрещён;
3. новое точное сообщение найдено — доставка подтверждена.

Существующий `DurableRequestLedger` уже обеспечивает правильное разделение выполнения и доставки: после локального выполнения повторяется только доставка сохранённого результата, а не локальная команда.

## Проверяемые свойства

Перед слиянием должны быть доказаны:

- сборка Windows;
- сохранение текущей папки между командами одного терминала;
- сохранение переменной среды между командами;
- повторяемое чтение того же абсолютного курсора;
- чтение новых данных без разрыва;
- уничтожение дочернего дерева процессов при закрытии;
- отсутствие слепого повтора после неопределённой отправки;
- восстановление сохранённого результата без повторного локального выполнения.
