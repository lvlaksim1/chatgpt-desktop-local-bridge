# RFC: перевод ChatGPT Desktop Local Bridge на прямой удалённый MCP

Статус: исследование и проектное решение; не является реализованным функционалом.
Дата: 2026-10-28.
Ветка продукта: main. Рабочая версия не изменена.

## 1. Цель

Обеспечить вызов локальных инструментов Windows из штатного интерфейса ChatGPT без передачи машинных конвертов через сообщения разговора, разбора HTML и использования задач планировщика как суррогатного транспорта. Сохранить пользовательскую подписку ChatGPT как способ общения с моделью: не переводить генерацию ответов на Responses API.

## 2. Подтверждённая архитектура Desktop Commander

По документации Desktop Commander Remote:
AI-клиент -> HTTPS MCP endpoint (Streamable HTTP, OAuth) -> облачный диспетчер -> авторизованный агент на компьютере -> локальный MCP-сервер -> ответ обратно по тому же маршруту.

Открытый исходный код локального агента DesktopCommanderMCP:
- src/remote-device/device.ts — жизненный цикл устройства, регистрация и обработка запросов;
- src/remote-device/device-authenticator.ts — OAuth device authorization + PKCE;
- src/remote-device/remote-channel.ts — Supabase Realtime, heartbeat, обнаружение обрывов, переподключение, согласование состояния запросов;
- src/remote-device/desktop-commander-integration.ts — MCP-клиент через stdio к локальному серверу, инструменты, контроль дочернего процесса.
- Hosted Remote MCP service — проприетарная часть, исходный код публично не доступен.

Это **не** «скрипт управления ChatGPT в браузере». Главный механизм — зарегистрированные инструменты, стандартный MCP и постоянно доступный агент устройства.

Источники:

## 3. Состояние нашего проекта на 28.10.2026

В main:
- WPF/.NET 8 + WebView2;
- Bridge/ToolRouter.cs — полезная локальная реализация инструментов;
- Bridge/PermissionPolicy.cs — AUTO/ASK/DENY;
- Bridge/ProcessExecutionManager.cs — управляемое выполнение процессов;
- Bridge/DurableRequestLedger.cs — журнал запросов и результата;
- Bridge/McpManager.cs — **MCP-клиент** локальных сторонних stdio-серверов, а не MCP-сервер для ChatGPT;
- Bridge/BridgeHost.cs и Web/bridge-adapter.js — транспорт через маркеры LOCAL_BRIDGE_REQUEST_V1/RESULT_V1 в обычных сообщениях;
- ScheduledTasks/* — служебная зависимость local.intent от серверной задачи ChatGPT.

Уже имеющиеся инструменты и управление разрешениями следует переиспользовать. Нельзя объявлять готовым удалённый MCP только потому, что McpManager уже поддерживает stdio.

## 4. Целевая архитектура

~~~text
ChatGPT (с подключённым собственным MCP-приложением)
         |
         | MCP Streamable HTTP, OAuth
         v
Remote MCP Gateway (наш сервер HTTPS, авторизация и маршрутизация)
         |
         | защищённое исходящее соединение агента
         v
Local Agent (Windows, в составе нашего приложения)
         |
         | локальный типизированный интерфейс / MCP stdio
         v
ToolRouter + PermissionPolicy + DurableRequestLedger + ProcessExecutionManager
         |
         v
Файлы, Git, процессы, приложения Windows
~~~

### Локальная часть

1. Вынести независимый от браузера исполнитель в сервис с интерфейсом ExecuteToolAsync(tool, args, callId, cancellationToken).
2. Реализовать MCP-сервер с tools/list и tools/call и полноценными JSON Schema для аргументов. Не превращать подсказки ArgsExample из ToolRouter в псевдо-схемы.
3. Разделить UI и фоновый агент. WPF отвечает за настройки, диалоги ASK, журнал, статус, STOP. Агент работает независимо от открытого диалога WebView2.
4. Подключить входящие вызовы к существующим PermissionPolicy, ToolRouter, DurableRequestLedger. Модифицирующие операции должны быть привязаны к callId, авторизованному пользователю и устройству.
5. Для ASK обеспечить асинхронный ответ из WPF через Dispatcher. При отсутствии интерфейса — детерминированное отклонение или заранее заданная политика, а не скрытое выполнение.
6. Исключить local.intent из нового пути: модель самостоятельно выбирает MCP-инструмент; отдельный планировщик больше не нужен.

### Удалённая часть

- HTTPS MCP Streamable HTTP endpoint, аутентификация, выбор устройства.
- OAuth 2.x с PKCE для клиента ChatGPT; привязка пользователя и устройства.
- Агент сам открывает исходящее TLS-соединение; входящие порты Windows не открываются.
- Постоянные идентификаторы вызовов, очередь, дедлайны, отмена, контроль подключения.
- Повторная доставка результата допустима; повторное выполнение уже начатого изменяющего действия без подтверждённого состояния — нет.
- При отсутствии агента — явный DEVICE_OFFLINE, не неограниченное ожидание.
- Логи содержат этапы и идентификаторы, но не токены/секреты или полные персональные документы.

Supabase не обязателен. Его Realtime — одна из реализаций обратного канала; для нашей системы допустим собственный WebSocket-диспетчер с устойчивым журналом запросов.

## 5. Два варианта доставки

**Вариант A — пилот через Secure MCP Tunnel.**
Самый короткий путь для доказательства работы: собственный локальный MCP-сервер и официальный tunnel-client. Не нужен собственный облачный брокер и не требуется открывать входящие порты. Но требуется связка OpenAI Platform/tunnel permissions, runtime API key и разрешение ChatGPT на добавление собственного MCP-сервера; это инфраструктурная авторизация, а не необходимость платить за генерацию ответов через API. Возможность добавления и вызова инструментов зависит от плана/рабочей области ChatGPT. Проверить доступность до разработки всего решения.

Документация: https://developers.openai.com/api/docs/guides/secure-mcp-tunnels

**Вариант B — самостоятельный облачный шлюз.**
Обычный защищённый remote MCP endpoint, собственная учётная запись, регистрация устройств, отдельный исходящий агент, OAuth и маршрутизация. Подходит для самостоятельного распространяемого продукта и не зависит от услуг Desktop Commander. Сложнее в эксплуатации, нужен постоянно работающий сервер. Если пользовательская цель — только личный доступ из имеющегося ChatGPT, сначала проверить вариант A.

**Вариант C — использовать установленный Desktop Commander без дублирования.**
Сейчас уже возможно выполнять действия на ПК из ChatGPT через подключённый Remote Desktop Commander. Это рабочий путь для задач пользователя, но он не превращает наш bridge в самостоятельный продукт: логика облачного соединения остаётся у стороннего провайдера.

## 6. Критическое ограничение совместимости ChatGPT

Нельзя рассчитывать, что JavaScript внутри WebView2 самостоятельно зарегистрирует произвольный MCP-инструмент в модели. Прямой MCP-вызов возможен, только когда соответствующее приложение/сервер действительно подключено и разрешено ChatGPT.

У собственных MCP-приложений есть плановые и административные ограничения, в том числе на write/modify-инструменты. Успешная работа уже опубликованного Desktop Commander не доказывает доступность личной публикации собственного MCP-приложения. Это отдельный Gate 0, проверяемый в **том аккаунте ChatGPT и том режиме**, для которого создаём продукт. Источник: https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt

## 7. Последовательность реализации и условия приёмки

**Gate 0. Доступ ChatGPT к собственным инструментам.**
Проверить реальное создание/подключение собственного тестового MCP, вызов read-only и разрешённость write-инструментов. Если write ограничен тарифом, не скрывать блокер и не заменять официальный MCP внутренним API ChatGPT.

**M1. Локальный MCP.**
Отдельный исполняемый сервер под Windows, tools/list, вызов system.info и fs.list через существующий ToolRouter. Проверка JSON Schema, пути/разрешений, ошибки и отмены. Не затрагивать прежний рабочий путь.

**M2. Удалённый транспорт.**
Подключить A (для пилота) либо B (для продукта). Показать реальный вызов из обычного ChatGPT, ответ в том же чате и выполнение на ПК. Без LOCAL_BRIDGE_* сообщений.

**M3. Запись и процессы.**
Доступ к fs.write_text и process.run по существующим разрешениям. Проверить ASK, отказ, STOP, длительное выполнение, размер результатов, обрыв во время вызова, защиту от дублирования.

**M4. Продуктовый интерфейс.**
Вкладка «Удалённое подключение» в WPF: состояние агента, аккаунт/устройства, тест соединения, последние операции, разрешения, отключить/отозвать доступ. Не требовать открытого окна чата.

**M5. Миграция.**
После успешного E2E переключить основной путь на MCP. LOCAL_BRIDGE_REQUEST_V1 и WebView2 DOM-adapter удалить или перевести в явно ограниченный режим совместимости только после приёмки.

## 8. Нефункциональные требования

- Разделять доверие: авторизация ChatGPT, привязка устройства, разрешение операции в Windows — три разные проверки.
- Минимально необходимые права локального процесса; исходное ограничение областей файловой системы.
- Для изменения файлов — резервирование вызова и состояние результата до ответа модели.
- Разрешать отмену при закрытии клиента и остановке пользователем; долговременные задания — через независимый job ID.
- Разделять уровни логирования, исключить секреты из GitHub/публичных журналов и телеметрии.
- Проверять работу после перезапуска UI, агента, сети и ПК; не создавать две копии агента.
- Никаких изменений пользовательских задач ChatGPT, переписывания скрытого backend API или эмуляции нажатий в ChatGPT как основного транспорта.

## 9. Решение

**Выбрана архитектура MCP-first.** Текущий Windows-исполнитель сохраняется. Для связи с ChatGPT используется самостоятельный удалённый MCP-канал (вариант A для быстрого технического пилота, вариант B для распространяемого продукта). Первое обязательное действие — Gate 0: подтверждение реальной доступности custom MCP tools в целевом ChatGPT. До этого времени не переписывать и не ломать работающую WPF-версию.

Документ — техническое исследование, не утверждение об успешном развёртывании нового MCP.
